# Глава 2. Проектирование программного средства

## 2.1. Анализ требований и варианты использования

Программное средство управления бюджетом и анализа исполнения сметы в научно-исследовательском институте предназначено для автоматизации следующих бизнес-процессов: планирования бюджета по формам Министерства финансов Республики Беларусь, учёта фактических расходов, проведения план-фактного и факторного анализа отклонений, формирования аналитической отчётности и поддержки управленческих решений.

На основе анализа предметной области и требований методических указаний к курсовому проекту были сформулированы функциональные и нефункциональные требования.

**Функциональные требования:**
1. Аутентификация пользователей и разграничение доступа по ролям.
2. Управление пользователями, отделами, проектами, статьями расходов.
3. Создание, редактирование, утверждение и отклонение смет по формам Министерства финансов.
4. Установка и контроль лимитов бюджетных обязательств.
5. Ввод фактических расходов с привязкой к первичным документам.
6. Сверка фактических расходов и закрытие отчётных периодов.
7. План-фактный анализ и факторный анализ методом цепных подстановок.
8. Подача и рассмотрение заявок на расход.
9. Формирование, утверждение и выгрузка аналитических отчётов.
10. Регистрация управленческих решений.
11. Ведение журналов действий и ошибок.
12. Резервное копирование базы данных.

**Нефункциональные требования:**
1. Клиент-серверная архитектура с многопоточным сервером.
2. Хранение настроек в конфигурационном файле, а не в исходном коде.
3. Защита передаваемых данных и паролей пользователей.
4. Обработка исключительных ситуаций с возвратом корректных HTTP-статусов.
5. Ведение журнала аудита операций и ошибок сервера.
6. Кроссплатформенность серверной части.

## 2.2. Архитектура программного средства

Программное средство построено по клиент-серверной архитектуре с разделением на три слоя: слой представления (клиентское приложение), слой бизнес-логики и слой доступа к данным (серверное приложение), а также слой хранения (система управления базами данных).

Клиентское приложение реализовано на платформе Windows Presentation Foundation с использованием паттерна Model-View-ViewModel. Серверное приложение выполнено в виде консольного приложения ASP.NET Core Web API, обрабатывающего HTTP-запросы параллельно. Взаимодействие между клиентом и сервером осуществляется по протоколу TCP/HTTP с обменом данными в формате JSON посредством REST-интерфейса.

Для хранения данных используется система управления базами данных PostgreSQL версии 18. Доступ к данным реализован через объектно-реляционное отображение Entity Framework Core с драйвером Npgsql.

6. **Типы денежных полей** — `numeric(18,2)` для сумм и `numeric(18,2)` для количеств и цен.

## 2.4. Проектирование сценариев работы

Для ключевых бизнес-процессов разработаны диаграммы последовательности. Диаграмма входа пользователя в систему приведена на рисунке 2.4.

**Рисунок 2.4 – Последовательность «Вход пользователя в систему»**

Сценарий входа реализует следующие бизнес-правила:

1. При неверном пароле счётчик неудачных попыток увеличивается на единицу.
2. После третьей неудачной попытки учётная запись блокируется на пятнадцать минут (значение настраивается в `appsettings.json`).
3. При активной блокировке запрос возвращает статус `423 Locked` даже при верном пароле.
4. При успешном входе счётчик неудачных попыток сбрасывается, создаётся сессия с маркёром доступа, запись о входе фиксируется в журнале аудита.

Диаграмма последовательности создания и утверждения сметы приведена на рисунке 2.5.

**Рисунок 2.5 – Последовательность «Создание и утверждение сметы»**

При создании сметы выполняются следующие проверки:

1. Роль пользователя — только «Главный экономист» (атрибут `[AuthorizeRole]`).
2. Существование проекта с указанным идентификатором.
3. Отсутствие дубликата — на один проект по одной форме за один год без родительской сметы может быть создана только одна смета.
4. Наличие хотя бы одной статьи расходов.
5. Неотрицательность плановых сумм, лимитов, количеств и цен.

При утверждении сметы проверяется, что её текущий статус — «На утверждении», и что она содержит хотя бы одну статью. При успешном утверждении статус меняется на «Утверждена», фиксируется дата утверждения, создаётся запись в журнале аудита.

## 2.7. Разграничение доступа и защита информации

В программном средстве реализованы четыре механизма защиты информации.

**Первый механизм — хранение паролей.** Пароли пользователей не хранятся в открытом виде. При создании учётной записи генерируется криптографически стойкая соль размером тридцать два байта, которая сохраняется в поле `User.PasswordSalt`. Хеш вычисляется по алгоритму SHA-256 от конкатенации соли и пароля и сохраняется в поле `User.PasswordHash`. Сравнение хешей при входе выполняется за постоянное время с использованием метода `CryptographicOperations.FixedTimeEquals`, что исключает атаки по времени выполнения.

**Второй механизм — блокировка после неудачных попыток.** После трёх неудачных попыток входа учётная запись блокируется на пятнадцать минут. Оба параметра настраиваются в файле `appsettings.json` и могут быть изменены администратором через экран «Настройки».

**Третий механизм — ролевое разграничение доступа.** Каждый эндпоинт серверного приложения защищён атрибутом `[AuthorizeRole]` с указанием списка разрешённых ролей. При отсутствии или просрочке маркёра доступа возвращается статус `401 Unauthorized`, при недостатке прав — `403 Forbidden`.

**Четвёртый механизм — шифрование передаваемых данных.** Для защиты тела запроса реализован класс `AesEncryptor` на основе алгоритма AES-256-CBC. Ключ шифрования и вектор инициализации задаются в файле `appsettings.json`. Шифрование продемонстрировано на эндпоинте `POST /api/auth/login-encrypted`, принимающем зашифрованный JSON с логином и паролем.

Дополнительно ведётся журнал аудита (`AuditLog`), в котором фиксируются все значимые операции: вход в систему, создание и редактирование записей, утверждение и отклонение документов, резервное копирование. Журнал доступен администратору через экран «Журналы».

## 2.8. Математическое ядро программного средства

Математическое ядро программного средства реализует семь формул план-фактного и факторного анализа.

**План-фактный анализ.** Абсолютное отклонение фактических расходов от плановых рассчитывается по формуле:

Δ = Факт − План,  (2.1)

где Факт — фактическая сумма расходов; План — плановая сумма расходов.

Относительное отклонение рассчитывается по формуле:

Δ% = ((Факт − План) / План) × 100 %.  (2.2)

Если плановая сумма равна нулю, относительное отклонение принимается равным нулю для исключения деления на ноль.

**Факторный анализ методом цепных подстановок.** Для статьи «Материалы» стоимость определяется произведением количества на цену: Стоимость = Количество × Цена. Влияние изменения количества на общее отклонение рассчитывается по формуле:

ΔQ = (Q_факт − Q_план) × P_план,  (2.3)

где Q_факт — фактическое количество; Q_план — плановое количество; P_план — плановая цена.

Влияние изменения цены рассчитывается по формуле:

ΔP = Q_факт × (P_факт − P_план),  (2.4)

где P_факт — фактическая цена.

Для статьи «Фонд оплаты труда» фонд определяется произведением численности на среднюю заработную плату: Фонд = Численность × Зарплата. Влияние изменения численности рассчитывается по формуле:

ΔЧ = (Ч_факт − Ч_план) × З_план,  (2.5)

где Ч_факт — фактическая численность; Ч_план — плановая численность; З_план — плановая средняя заработная плата.

Влияние изменения заработной платы рассчитывается по формуле:

ΔЗ = Ч_факт × (З_факт − З_план),  (2.6)

где З_факт — фактическая средняя заработная плата.

Проверка корректности факторного анализа выполняется по формуле:

Δ = ΔQ + ΔP (или Δ = ΔЧ + ΔЗ),  (2.7)

то есть сумма вкладов всех факторов должна равняться общему отклонению с точностью до одной копейки.

Все семь формул реализованы в классе `AnalysisService` в виде чистых методов, не зависящих от базы данных, что позволило покрыть их модульными тестами.
