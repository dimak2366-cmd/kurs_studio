# ГЛОБАЛЬНАЯ СПРАВКА ПРОЕКТА (MASTER REFERENCE)

## 1. ПАСПОРТ КУРСОВОГО ПРОЕКТА
**Тема:** Сетевое программное средство управления бюджетом и анализа исполнения сметы в научно-исследовательском институте.
**Дисциплина:** Проектирование программного обеспечения (ПСП).
**Среда разработки:** Microsoft Visual Studio 2022 (C#).
**Цель работы:** Разработать клиент-серверное приложение для автоматизации планирования бюджета (по формам Министерства финансов Республики Беларусь), учета фактических расходов и проведения факторного анализа отклонений.

## 2. АРХИТЕКТУРА И СТЕК ТЕХНОЛОГИЙ (СТРОГО)
Проект выполняется строго по требованиям методички (клиент-серверная архитектура с многопоточным сервером):
*   **Клиент (Frontend):** C# (.NET 8), Windows Presentation Foundation (WPF), паттерн MVVM.
*   **Сервер (Backend):** C# (.NET 8), консольное приложение ASP.NET Core Web API.
*   **База данных (БД):** PostgreSQL.
*   **ORM:** Entity Framework Core (Npgsql).
*   **Взаимодействие:** REST API, обмен данными в формате JSON по протоколу TCP/HTTP.

### Жесткие требования методички (Обязательно к реализации):
1.  **Многопоточность:** Сервер должен обрабатывать запросы от нескольких клиентов параллельно (каждый запрос в отдельной задаче/потоке).
2.  **Настройки сервера:** Адрес, порт и строка подключения к БД должны задаваться в конфигурационном файле (например, `appsettings.json`), а не хардкодиться в исходниках.
3.  **ООП-техники:** Собственная иерархия классов (не менее 5), интерфейсы, абстрактные классы, инкапсуляция, перегрузка/переопределение методов, статические методы, сериализация, обработка исключительных ситуаций.
4.  **Паттерны:** Обязательно использовать не менее 2-х паттернов (например, «Репозиторий» для работы с БД, «Команда» для API и «Одиночка» для конфигурации).
5.  **Варианты использования:** Не менее 12 высокоуровневых вариантов использования (исключая тривиальное добавление/удаление в БД). 
6.  **БД:** Не менее 5 связанных таблиц, нормализация до 3-й нормальной формы (3НФ), обеспечение ссылочной целостности (Foreign Keys).
7.  **Безопасность:** Механизм авторизации (роли), хранение паролей в виде хеша (например, SHA-256 с солью), шифрование передаваемых данных, резервное копирование БД.

## 3. РОЛИ И ФУНКЦИОНАЛ (Планируемый функционал)
В системе предусмотрено 3-4 роли (в зависимости от требований, берем 4):
1.  **Администратор:** Управление пользователями, справочниками, ролями, резервное копирование БД, настройки системы.
2.  **Главный экономист (или экономист ПЭО):** Создание смет по формам Минфина, ввод плановых показателей, импорт факта, запуск факторного анализа, выгрузка отчетов.
3.  **Руководитель проекта (заведующий отделом/лабораторией):** Просмотр смет и аналитики только по своему проекту (НИОКР), подача заявок.
4.  **Бухгалтер:** Ввод фактических данных (кассовых расходов), сверка, формирование проводок.

## 4. ПРЕДМЕТНАЯ ОБЛАСТЬ И ЗАКОНОДАТЕЛЬСТВО РБ
**Предметная область:** Бюджет и сметы научно-исследовательского института. Сметы формируются по строго утвержденным формам Министерства финансов Республики Беларусь.
**Нормативная база (Основные источники для ссылок):**
*   Постановление Министерства финансов РБ от 15.10.2010 № 111 (утверждает 16 форм, например: 1-57, 1-58, 1-60, 1-48, 2-смета и др.).
*   Закон РБ «О научной деятельности» от 21.10.1996 № 708-XIII.
*   Постановление Совета Министров РБ от 12.08.2010 № 1196 (о финансировании).
*   Инструкция по бухгалтерскому учету в бюджетных организациях (Постановление Минфина № 25 от 30.04.2012) — регламентирует счета учета фактических затрат на НИОКР.

**Ключевые понятия:**
*   *Смета* — план расходов по конкретному проекту (НИОКР).
*   *Статья расходов* — строка сметы (ФОТ, Материалы, Услуги сторонних организаций, Командировочные и т.д.).
*   *Фактический расход* — реально потраченные деньги (по данным бухгалтерии).
*   *Лимиты бюджетных обязательств (ЛБО)* — максимальная сумма, которую можно потратить.

## 5. МАТЕМАТИЧЕСКОЕ ЯДРО (Алгоритмы анализа)
Это главная фича программы. Мы считаем отклонения и находим их причины.

### 5.1. План-фактный анализ
*   Абсолютное отклонение: `Δ = Факт - План`
*   Относительное отклонение: `Δ% = ((Факт - План) / План) * 100%`

### 5.2. Метод цепных подстановок (Факторный анализ)
**Для статьи «Материалы»:** `Стоимость = Количество (Q) × Цена (P)`
*   Влияние количества: `ΔQ = (Q_факт - Q_план) * P_план`
*   Влияние цены: `ΔP = Q_факт * (P_факт - P_план)`

**Для статьи «Фонд оплаты труда (ФОТ)»:** `ФОТ = Численность (Ч) × Средняя зарплата (З)`
*   Влияние численности: `ΔЧ = (Ч_факт - Ч_план) * З_план`
*   Влияние зарплаты: `ΔЗ = Ч_факт * (З_факт - З_план)`

## 6. МОДЕЛЬ БАЗЫ ДАННЫХ (Концептуальная)
Таблицы (минимум 5 связанных):
1.  `Projects` (Проекты НИОКР) — ID, Название, Шифр, Даты.
2.  `Smeta` (Сметы) — ID, ProjectID, КодФормыМинфина, Год, Статус.
3.  `ExpenseItems` (Статьи смет) — ID, SmetaID, Наименование, ПлановыйКодКОСГУ, ПлановаяСумма.
4.  `ActualExpenses` (Фактические расходы) — ID, ExpenseItemID, Дата, ФактическаяСумма, НомерДокумента.
5.  `Users` (Пользователи) — ID, Логин, ХэшПароля, Роль (Admin, Economist и т.д.).
6.  `Roles` (Роли) — ID, Название.

## 7. ПРАВИЛА ГЕНЕРАЦИИ ТЕКСТА (Для Word / Документации)
1.  **СТРОЖАЙШИЙ ЗАПРЕТ НА АББРЕВИАТУРЫ.** В тексте курсовой нельзя писать «НИОКР», «БД», «АСФР», «ЛБО». Только полные формы: «научно-исследовательские и опытно-конструкторские работы», «база данных», «автоматизированная система финансовых расчетов», «лимиты бюджетных обязательств». Сокращения допустимы только на UML-диаграммах.
2.  **Шрифты и отступы:** Times New Roman, 14 pt, межстрочный интервал 1.5 (18 пт), выравнивание по ширине, красная строка 1.25 см.
3.  **Формулы:** Вставлять через редактор формул Word. Справа в скобках нумерация (например, (1.1)). Под формулой расшифровка переменных (начинается со слова «где»).
4.  **Ссылки на источники:** В тексте в квадратных скобках `[1]`. В конце — список по ГОСТ.
5.  **Стиль:** Академический, без воды, от третьего лица.

## 8. ПРАВИЛА ГЕНЕРАЦИИ КОДА (Для IDE)
1.  **Разделение слоев:** Код WPF не должен содержать SQL-запросов. Код Web API не должен содержать XAML.
2.  **Entity Framework Core:** Использовать Code-First подход (миграции) или Database-First (если проще). Сущности должны быть чистыми классами C#.
3.  **Обработка ошибок:** Обязательно использовать блоки `try-catch` и возвращать корректные HTTP-статусы (200, 400, 401, 404, 500) из контроллеров API.
4.  **Логирование:** Сервер должен писать логи (например, в консоль или файл) о входящих запросах и ошибках.
